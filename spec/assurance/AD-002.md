# AD-002: tl-mltl infinite-trace crate boundary

## System Boundary

tl-mltl's trusted core (AD-001) consumes `tl-syntax.formula/v1` bounded graphs
and finite traces, and that admitted surface is the whole of its formula input.
Lasso-word acceptance, fairness admission, and the inductive infinite-trace
semantics tl-mltl#68 tracks sit outside this boundary, in a separate provider
under the `quire.temporal.infinite-trace/v1` facet that consumes the
`tl-syntax.formula-unbounded/v1` edition independently and registers against
tl-syntax's `tl-syntax.liveness/v1` capability on its own.

## Views

The bounded semantic view (AD-001) is unchanged: closed and prefix evaluation,
horizon analysis, and monitor mapping continue to operate on
`tl-syntax.formula/v1`. The infinite-trace provider is an external view,
referenced by facet and capability identity —
`quire.temporal.infinite-trace/v1` and `tl-syntax.liveness/v1` — wherever this
crate's spec must say where infinite-trace evaluation lives. No module,
dependency, or feature flag in this crate reaches into it, and it reaches
nothing in this crate.

## Decisions

The boundary is decided from tl-mltl's own pre-existing scope, not adopted as
a new position: `spec/spec.md`'s Out-of-Scope section already excluded
"unbounded LTL" before this ticket, and the entire bounded-evaluator
architecture (closure-as-false, checked horizon expansion, pending-verdict
machinery) presupposes a finite trace throughout. quire-specification's own
AD-002 models infinite-trace analysis as provider-independent ("Providers
prove correspondence and soundness; finite monitors cannot overclaim"), and
tl-mltl is exactly the finite monitor that line describes, so infinite-trace
evaluation is allocated to a separate provider rather than to an in-repo
facet.

The provider is identified here by the facet and capability it binds, which is
what the boundary actually depends on: it consumes
`tl-syntax.formula-unbounded/v1` under `quire.temporal.infinite-trace/v1` and
is the single registrant for `tl-syntax.liveness/v1`. That identity is stable
regardless of which crate carries the implementation.

## Open Questions

Which crate carries the infinite-trace provider is an owner decision, and this
architecture description records it as open. No existing tl-mltl,
tl-syntax, or quire-specification artifact names such a crate: tl-syntax
FR-290/FR-291 name only the `tl-syntax.liveness/v1` capability identity, and
quire-specification AD-002/AD-003 name only the
`quire.temporal.infinite-trace/v1` facet and a provider-independent contract.
This description therefore mints no crate name; the owner records the chosen
name when the implementation is staffed, and only the facet-facing and
capability-facing references in FR-027 through FR-029 need to name it then.

## Risks

Until a provider registers for `tl-syntax.liveness/v1`, tl-mltl#68's
lasso/fairness/infinite-trace scope has no implementation behind it; every
`tl-syntax.formula-unbounded/v1` document settles `unsupported` with a warning
naming that capability, which is the specified state of this boundary rather
than a defect. Because the provider is referenced only by facet and capability
identity, an owner's later crate-name decision touches these spec files alone
and never tl-mltl's own evaluator.
